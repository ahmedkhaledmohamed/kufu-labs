NWB stream integrity during inspection

Status: lab-published patch and constructed-data replay; upstream review package prepared locally. No upstream PR, researcher validation or real-recording evaluation. The implementation and learning plan explains the next milestones.

Reported problem and beneficiary

NWB Inspector #771 reports that inspecting an in-memory NWB file before writing can consume buffered data. The subsequent writer saves without raising a write error, but part of the dataset becomes zeros. Researchers and engineers converting streamed neurophysiology recordings could therefore save altered data while performing an apparently observational step.

The report describes affected conversions; it does not measure how common the problem is. Our local baseline also returns Inspector ERROR messages while still allowing the damaged data to be saved. We do not describe this observed local path as inspection passing silently.

Local before and after

The replay calls the actual Inspector, then writes and reads a real HDF5 or Zarr NWB file. It uses positive constructed int16 arrays with two channels at 100 Hz. These are software fixtures, not measured neural signals or a biological simulation. No recordings, subjects or model weights are involved.

Implementation and integration

Upstream baseline: NWB Inspector e6d968a, package version 0.7.3. The local patch modifies the existing shape helper and adds regression tests in that project. It re-exports HDMF 6.2.0's existing get_data_shape helper instead of maintaining an Inspector-specific copy. That helper already supports the declared shape of the tested wrapped chunk iterators and the current shape of stored resizable datasets. It does not add a general policy for arbitrary single-pass iterators.

The supported integration is the existing inspect_nwbfile_object conversion workflow. No new application, plugin or monkey patch is required. Issue #760 proposes reusing HDMF's helper; HDMF PR #1606 proposes a related wrapper fix and was open when checked. The existing-helper substitution and the pinned dependency PR each preserved all values across the 24-case constructed replay. The helper substitution also passed 330 existing unit tests, with 5 skipped, before this source patch was prepared. We selected reuse of the released helper for the smaller maintenance surface; upstream may prefer a different design.

Parameterized execution lab

Execution lab uses experiment.py to generate synthetic signals with editable rows, channels, buffer size, seed, pattern, file backend and iterator type. A boundary batch generates cases below, at and above the buffer size, plus a larger case. Generating the input plan is local; pressing Run submits scientific execution to Vercel.

Vercel Functions validate requests and publish to Vercel Queues. The worker starts a non-persistent, one-vCPU Vercel Sandbox, prepares the pinned upstream revision and patch, installs complete CPython 3.13.9 using uv 0.9.5 and the pinned requirements, then disables network access. Each revision gets fresh inspected and uninspected objects, iterators and files. Every value, shape and dtype is compared. Private Blob storage retains reports, logs and an archive of actual NumPy arrays and file round trips after the Sandbox stops. The lab accepts parameters, not recordings or arbitrary code.

On 28 October 2026, a direct SDK run of the local implementation in a real Vercel Sandbox completed in 16.301 seconds and stopped its VM. A 500-row, two-channel HDF5 ramp changed 300 baseline rows and zero patched rows. A seeded random 51-row, three-channel Zarr input with a generic iterator changed 51 baseline rows and zero patched rows. All four uninspected controls preserved every value. The initial hosted runtime lacked _bz2; installing complete pinned CPython resolved that failure without disabling Zarr. This direct SDK result does not establish that the deployed queue/API/storage flow has passed.

Local parameterized verification also covers one row, three channels with Zarr, the maximum 2,000 × 8 shape and seed boundary, and alternating-sign values. CI repeats those real round trips. API checks cover validation, cross-site rejection, duplicate delivery, failed execution and result classification. Browser checks use local API doubles and real scientific reports; they launch no Sandbox. The deployment gate separately submits real HDF5 and Zarr jobs to the protected Vercel preview, waits for the actual Queue/Sandbox worker, verifies saved comparisons and checks the private download hash before production promotion. The deployed gate passed before promotion in merged-main run 40877666335.

The execution page also displays timestamped progress reported by the worker: queue wait, environment setup, baseline/patched runs, output packaging, compute shutdown and saving the result bundle. Running snapshots are private; completed and failed results retain the final history. Elapsed time is calculated from those timestamps, with no estimated completion percentage. Production run 9ebc0340-6763-4a6f-b05f-973270fde296 retained all 13 stages; an independent audit verified its private archive hash, stopped Sandbox and protected API.

Bounds are four cases per submission, 2,000 rows × 8 channels per case, four minutes per Sandbox, one concurrent queued worker and ten submissions per UTC day shared by preview, production and deployment verification. Reusing a request ID and a claimed queue message prevents duplicate VM launches. Interrupted workers become an explicit interrupted status. Verification and limits

The replay passed locally on Python 3.13.2 with PyNWB 4.2.0, HDMF 6.2.0, HDMF-Zarr 0.14.0, h5py 3.16.0, Zarr 3.4.2 and NumPy 2.5.4. The requirements retain the public package versions from this environment; no local editable paths are included. The exact Inspector source is installed separately.

The broader local unit run passed 341 tests, including 11 new stream/shape cases, with 5 skipped. Ruff and Black passed on the two changed upstream files. This includes checking that an existing resizable HDF5 dataset reports its current shape, and that existing time-series validation still detects its tested failures. Broader unit regression results and final patch reapplication are recorded in verification.

The initial scope does not cover real recordings, every NWB extension or iterator implementation, all dependency versions, performance at recording scale, upstream acceptance or researcher benefit. Shape metadata itself may be incorrect. Preserving values does not prove acquisition quality or scientific validity. The follow-up workflow runs this replay and the unit regressions inside the existing required scientific-contract check, using an isolated environment. The web build consumes that run's JSON results. The required check and deployment passed on merged main in run 40613968067; packaged and production results were independently verified.

Science to understand alongside this patch

A time series is a sequence of measurements indexed by time. Here a row holds two constructed channel values and 100 Hz means 100 samples per second. In a real recording, channel meaning and units depend on the measurement method: spikes, local field potentials and EEG are different representations and cannot be treated interchangeably.

NWB organises measurements and associated metadata so they can be stored and reused. Chunk iterators allow conversion without loading an entire recording into memory. Advancing a single-pass iterator changes what the next consumer receives. An inspection step should preserve the stream for the writer. That is the specific software invariant tested here, not a new neuroscience finding.
