Inspect why overlapping poses are removed

Two pose predictions can overlap even when they describe different animals or different body-part arrangements. The researcher needs to understand why a duplicate filter keeps one and removes another.

Demonstrated; user problem not yet solved

Who encounters it and why it matters

Researchers proofreading overlapping animal-pose predictions in SLEAP.

Make duplicate-filter decisions inspectable so a person can understand a setting. Better choices and time saved remain unmeasured.

Science and terms

A pose is an estimated set of body-part positions. Tracking software can produce multiple candidate poses in one video frame. A duplicate filter compares candidates and can remove a later candidate when their similarity exceeds a chosen threshold.

IoU
Intersection over union: how much two bounding boxes overlap relative to their combined area.
OKS
Object keypoint similarity: a score based on corresponding body-part positions and scale. This implementation’s score can depend on comparison direction.
Suppression
Removing a candidate pose from the filter output; this is not evidence that it was biologically wrong.

Where the problem appears

  1. Predict body-part positions

    The host produces candidate poses and confidence scores.

  2. Compare overlapping candidates

    A chosen metric assigns pairwise similarity.

  3. Apply the threshold

    Score order and earlier decisions affect which candidates remain.

  4. Inspect the decision

    The prototype exposes the selected pair and full-frame context.

Evidence and existing tools

SLEAP has QC, editing and filter settings; pinned audit found no pairwise comparison panel.

  • Feature request #2816
  • Original discussion #2815

The solution being tested

Kufu’s prototype adds an overlay, pair measurements, threshold boundaries and score-order context around an unchanged filter. It is a browser demonstration of an inspection capability. It is not integrated into the SLEAP application and does not improve the prediction model.

Local demo now; future read-only SLEAP selection adapter or explicit pose import.

What the inspector adds

Both views use the same fixed input and filter. For the swapped-label example at IoU threshold 0.8, A is retained and B is suppressed in both views. The added capability is explanation.

Validation and limits

7 frozen synthetic cases; 498 actual FilterPipeline calls and 168 browser boundary views passed.

What remains unverified

No SLEAP selection/import integration or actual researcher task. No node-exclusion support or arbitrary pose input.

What would count as resolving it

Correctly inspect existing host instances with matched node/score semantics, then show useful decisions in an authorised real workflow without increasing mistaken removals.

Next step
